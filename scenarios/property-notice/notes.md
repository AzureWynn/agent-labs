# 场景：小区物业公告 + 维修工单

> 数据现在位于 `v2/scenarios/property-notice/`。本文保留 2026-10-21 的试点记录，并追加 v2 复现结果。
>
> Pack C 主数据集已扩到 60 篇文档 / 30 条查询，见 `v2/scenarios/property-notice-60/notes.md`。
> 本文的 30 篇数字冻结，作为对照，不再改动。

## 为什么选它

我想找一个和原例完全不同的中文场景，要求：

- 实体多（楼号、日期、金额、责任人、状态）
- 同一类信息反复出现（多个"漏水/堵塞/电梯"工单）
- 有明确真值（每条查询都能指出正确文档）

物业公告正好满足：短文本、强结构化、日常语言。

## 与原例的差异

| 维度 | 原例 `_baseline` | 本场景 |
|---|---|---|
| 语言 | 英文 | 中文 |
| 领域 | 产品型号 / HTTP 错误码 | 物业公告 / 维修工单 |
| 文档数 | 14 | 30 |
| 查询数 | 7 | 18 |
| 结构 | 纯自然语言短句 | 编号 + 日期 + 楼号 + 金额 + 责任人 |
| 真值 | 原有标注 | 我手工标注 |

## 设计

- 公告 `P001~P010`：停水停电、电梯检修、燃气安检、消防演练、门禁升级、绿化、垃圾清运
- 工单 `T001~T012`：下水道、漏水、电梯异响、路灯、门锁、空调滴水、地锁、渗水、道闸、楼道灯、返味、按钮
- 费用 `F001~F003`：物业费、维修基金分摊、停车费
- 通知 `N001~N005`：业主大会、失物招领、宠物走失、高空抛物、电动车充电

查询里故意放了两类难点：

- 同义改写：`下水道返味` 对 `地下管道返味`
- 多文档答案：`6号楼外墙渗水要多少钱` 同时命中工单 `T008` 与费用 `F002`

## 第一次运行的结果（重要发现）

用 `SCENARIO=property-notice npm run eval`，得到：

| 方法 | Recall@3 | MRR | nDCG@3 |
|---|---:|---:|---:|
| BM25 | **0.0556** | 0.0759 | 0.0511 |
| Dense | 0.6389 | 0.5288 | 0.5208 |
| Hybrid-RRF | 0.6667 | 0.5288 | 0.5423 |

BM25 几乎归零。查 `src/tokenizer.ts` 后发现原因：

```ts
const TOKEN_RE = /[A-Za-z0-9._+#-]+@...|[A-Za-z]{2,}|[0-9]+/g;
```

正则只匹配拉丁字母和数字，中文整段被丢弃。例如：

```
"3号楼下水道堵了" → ["3"]
"工单：3号楼2单元厨房下水道堵塞" → ["3", "2"]
```

原来的英文语料看不出来，换成中文立刻暴露。

## 适配后

给分词器加 CJK 二元组（只影响中文，英文路径不变）：

```
"下水道堵塞" → 下水 水道 道堵 堵塞
"下水道堵了" → 下水 水道 道堵 堵了
```

| 方法 | Recall@3 前 | Recall@3 后 |
|---|---:|---:|
| BM25 | 0.0556 | **1.0000** |
| Dense | 0.6389 | 0.6389 |
| Hybrid-RRF | 0.6667 | 0.9444 |
| Hybrid-Weighted | 0.6667 | 0.9444 |
| Hybrid-RRF+Rerank | 0.6667 | 1.0000 |

## 这组数据说明了什么

1. **BM25 的问题不是算法，是分词**。同一份代码，只改分词，Recall@3 从 0.06 到 1.00。
2. **稠密检索没变**（0.6389），因为用的是英文嵌入模型 `nomic-embed-text`，
   中文语义匹配能力有限。这次没有换模型，保持变量单一。
3. **混合不一定比单路好**。适配后纯 BM25 是 1.00，Hybrid-RRF 只有 0.9444，
   加 rerank 才回到 1.00。也就是说在这个小语料上，融合把一个满分结果拉低了。
4. 结论只对**这个场景、这个样本量**成立。18 条查询，单次运行，不做统计显著性声明。

## 复现

v2 已复现五种方法（中文分词默认开启，dense 依赖本地 Ollama）：

```bash
npm run -w @book/lab-01-retrieval-pipeline eval
npm run -w @book/lab-01-retrieval-pipeline test
```

默认参数与 v1 一致：候选池 20、RRF k=60、dense/sparse 权重各 0.5、rerank 取融合前 10 条。

## BM25 参数与解释（lab 02）

lab 02 不跑 dense，只把 BM25 拆开看：查询词怎么切、每个词贡献多少、k1/b 改了排序会不会变。

```bash
npm run -w @book/lab-02-sparse-bm25 demo
npm run -w @book/lab-02-sparse-bm25 explain -- --query "3号楼停水"
npm run -w @book/lab-02-sparse-bm25 eval
npm run -w @book/lab-02-sparse-bm25 sweep
```

`eval`（k=5，k1=1.5，b=0.75）：Recall@5 1.000，MRR 0.917，nDCG@5 0.938。
`3号楼停水`、`摄像头坏了`、`下水道返味` 三条的正确答案在第 2 位。

`sweep` 扫 k1 ∈ {0.5, 1.0, 1.5, 2.0} × b ∈ {0, 0.25, 0.5, 0.75, 1.0}：

- Recall@5 全部是 1.000，参数不影响"能不能搜到"。
- MRR 只随 b 变：b=0 时 0.972，b>0 时 0.917；k1 从 0.5 到 2.0 没有改变排序。

两个具体案例：

1. `3号楼停水` 的真值是 P001（3号楼停水，33 个 token），
   默认 b=0.75 时 P010（6号楼清洗水箱停水，21 个 token）排第一。
   原因是 P010 更短，长度归一化后 `停水` 的贡献被放大；
   把 b 设成 0，P001 靠 `3` 出现两次回到第一。
2. `下水道返味` 的真值是 T011（地下管道返味）。
   T001 命中 `下水`/`水道`，T011 命中 `道返`/`返味`，各 2 个二元组；
   默认参数下 T001 5.7581、T011 5.6649，差距只来自文档长度（29 vs 30）。
   b=0 时两者分数完全相同，排序退回文档顺序，T011 仍然是第 2。

这说明：BM25 只能看字面重叠，重叠一样时它没有"意图"可用；
b 能改变"短文档优先"的程度，但不能补上语义。

## 局限

- 查询只有 18 条，且由我一个人标注，没有第二人复核。
- 嵌入模型是英文模型，中文稠密检索的数字不能代表中文嵌入模型的水平。
- BM25 的 1.00 是这个小语料上的结果，语料变大、查询变复杂后未必保持。
